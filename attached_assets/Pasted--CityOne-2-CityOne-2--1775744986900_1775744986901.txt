## 一、整改背景

第一批 PostgreSQL 迁移已完成并验证通过，第二批第 1 份《认证与账户体系整改》也已完成并验证通过。

当前已具备的基础：

* PostgreSQL 已正式接入
* 核心业务表已建立第一版基础
* coupons / mall-items / growth-points 已迁入 PostgreSQL
* admins / accounts / members 已从 JSON 迁移到 PostgreSQL
* 管理员登录、会员查询、账户查询已可真实走 DB

因此，当前第二批下一步应进入：

**入口与活动归因主链路整改。**

这是营销增长系统真正的业务主骨架。因为对增长系统而言，最关键的问题不是“页面有没有”，而是：

1. 用户从哪个入口进入
2. 进入后落到哪个落地页
3. 当前看到的是哪个 Banner / 哪组承接内容
4. 最终进入了哪个活动
5. 后续参与、领券、积分、订单是否能正确归因回入口与活动

如果 `entries / activities / landing / banners` 继续停留在 JSON 或假数据状态，那么整个增长系统即使页面能看，也无法做到真实增长归因。

---

## 二、整改目标

本次整改目标是把“入口 → 落地页 → Banner → 活动”这条营销主链路，从 JSON / 假数据 / 混合状态整改为 PostgreSQL 正式承接，并形成第一版真实可追踪的归因基础。

整改完成后，至少应实现：

### 1. 入口体系正式落库

* 各类入口对象不再依赖 JSON 文件
* 入口基本信息、状态、类型、关联落地页/活动具备正式表结构
* 后续可承接二维码入口、渠道入口、A 系统设备入口预留

### 2. 活动体系正式落库

* 活动列表、活动详情、活动状态、活动时间、活动承接关系具备正式表结构
* 后续活动参与、奖品、卡券、积分规则可有稳定主表依附

### 3. 落地页体系正式落库

* 落地页基本信息、模板类型、承接内容、关联入口/活动具备正式表结构
* 后续可支持不同入口落到不同落地页

### 4. Banner 体系正式落库

* Banner 不再只作为静态前端配置
* Banner 的位置、排序、跳转对象、关联活动/落地页等具备正式存储

### 5. 形成第一版主归因链路

至少形成以下关系：

* `entry` → `landing`
* `entry` → `activity`
* `landing` → `banner`
* `banner` → `activity`
* `activity` 可反查来源入口/落地页/Banner

## 六、整改实施要求

### 第一阶段：迁移设计

你需要完成：

1. 为 `entries`、`activities`、`landing`、`banners` 设计正式 PostgreSQL 表结构
2. 输出 migration / schema 变更
3. 明确 JSON → PostgreSQL 的迁移策略
4. 明确哪些历史字段保留、哪些废弃、哪些兼容

### 第二阶段：历史 JSON 数据迁移

你需要：

1. 找到当前对应 JSON 文件
2. 设计迁移脚本或 seed 脚本
3. 将历史入口、活动、落地页、Banner 数据导入 PostgreSQL
4. 对脏数据、空字段、重复键给出处理方式

### 第三阶段：接口读写切换

你需要：

1. 将相关 routes / services / repository 改为优先走 PostgreSQL
2. 移除或降级对 JSON 文件的主依赖
3. 保证入口列表 / 活动列表 / 活动详情 / 落地页 / Banner 读取链路走 PostgreSQL
4. 至少完成一条完整的入口 → 落地页/活动查询链路 DB 化

### 第四阶段：前端兼容承接

你需要：

1. 保证旧前端页面字段不崩
2. 对缺失字段做兼容处理
3. 如前端某些页面此前吃的是假数据，需改成真实接口字段承接
4. 不允许因为迁移导致活动页/入口页白屏

### 第五阶段：归因字段预留

你需要在合适位置预留：

* `source_entry_id`
* `source_activity_id`
* `source_banner_id`
* `source_channel_id`
* `device_code`
* `a_system_device_id`

注意：这次先做主链路与字段预留，不要求把后续所有订单/积分/领券归因一起全做完。
