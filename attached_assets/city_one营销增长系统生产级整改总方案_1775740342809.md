## 二、项目归类与当前目标

### 1. 项目归类

- 公司级总盘：龙码
- 当前优先商业项目：CityOne
- 当前整改对象：CityOne 营销增长系统
- 关联系统：A 系统（共享充电宝系统）

### 2. 当前目标

当前目标不是继续做技术内测，而是把营销增长系统整改为：

**可以与 A 系统旁路连接、并具备真实生产级运行基础的独立增长系统。**

这里的“生产级”至少包含：

- 数据落到正式数据库，不再依赖临时 JSON / 临时文件 / 混乱结构
- 图片、视频、素材走 OSS，不再混乱存放
- 数据归因真实可追踪
- 配置、活动、卡券、商品、订单、积分、分享等链路可落库、可查询、可审计
- 管理端与用户端主要功能链路可用
- 多语言方案按既定方案实施，不允许偏移成“手工三语录入模板”
- 与 A 系统的旁路连接具备后续接入条件

## 四、整改总原则

### 1. 不允许脱离真实代码重造一套

所有整改必须基于当前真实项目结构做定点修改。

### 2. 不允许继续使用“临时可跑”思路替代生产方案

任何本地 JSON、临时文件、无归因数据结构、无统一存储路径的方案，都只能视为临时内测方案，必须逐步整改。

### 3. 不允许偏移既定多语言方案

当前多语言方案必须遵循既定原则：

- 默认跟随用户设备 / 浏览器语言
- 支持手动切换中 / 泰 / 英
- 不是手工录入三套模板文本
- 可由 AI 翻译生成其它语言备份
- 管理端语言逻辑与用户端保持一致

### 4. 不允许在服务器直接手改业务代码

服务器仅做部署与验收，不做主要业务开发。

### 5. 不允许把两个独立系统混成一个工程

营销增长系统与 A 系统目前是：

- 同一服务器
- 分开部署
- 独立运行
- 后续通过旁路连接实现协同

## 五、整改总模块

本次整改分为六大模块。

### 模块一：PostgreSQL 正式接入整改

#### 目标

将当前营销增长系统后端正式接入阿里云 RDS PostgreSQL，替代临时性数据存储方式。

#### 整改内容

- 梳理当前后端实际数据存储方案
- 确认当前项目读取哪种数据库配置方式
- 将后端统一切换为 PostgreSQL
- 建立正式表结构
- 增加 migration / seed / 初始化脚本
- 确保活动、卡券、商品、订单、积分、用户、分享等主数据可落库

#### 产出物

- 数据库连接配置
- schema / migration
- 初始化脚本
- 数据模型说明
- 环境变量说明

#### 验收标准

- 后端在 Replit 可正常连接 PostgreSQL
- 关键表可创建
- 基础增删改查通过
- 推送部署后线上可正常读写数据库

---

### 模块二：OSS 正式接入整改

#### 目标

将营销增长系统中的图片、视频、活动素材、商品素材等文件统一接入 OSS。

#### 整改内容

- 梳理当前项目中所有文件上传点
- 统一改为上传至 OSS
- 统一回写数据库中的文件 URL / Key / Bucket / 业务关联信息
- 明确公开资源与私有资源边界
- 明确命名规则与目录结构

#### 产出物

- OSS 接入配置说明
- 上传模块代码整改
- 文件路径命名规则
- 数据库中的素材关联字段

#### 验收标准

- 管理端上传后文件真实进入 OSS
- 前端展示地址可用
- 数据库中可追踪文件归属

---

### 模块三：数据结构与数据归因整改

#### 目标

将系统从“功能页面存在但数据结构混乱”整改为“业务数据真实可追踪”。

#### 核心对象

至少覆盖：

- 用户
- 会员身份 / 标签
- 活动
- 活动参与记录
- 抽奖 / 奖品
- 卡券
- 商品
- 兑换订单
- 积分账户
- 积分流水
- 分享行为
- 来源渠道
- 入口二维码 / 入口实例
- 设备 / A 系统映射预留字段

#### 整改内容

- 梳理现有字段与页面关系
- 明确每个业务对象主表与关联表
- 明确归因字段：来源入口、来源活动、来源分享、来源渠道、来源设备等
- 补齐必要状态字段、时间字段、操作者字段

#### 验收标准

- 任一条订单 / 领取 / 分享 / 参与记录都可追溯来源
- 管理端能够查询主要业务数据
- 后期与 A 系统连接时有明确映射位

---

### 模块四：管理端与用户端功能整改

#### 目标

补全现有前后端链路，确保主要功能不是“页面有壳但缺真实承接”。

#### 管理端重点

- 活动中心
- 卡券管理
- 商品管理
- 积分管理
- 订单管理
- 上传素材管理
- 入口中心 / 二维码管理
- 数据看板 / 归因分析基础能力

#### 用户端重点

- 活动浏览与参与
- 卡券领取、展示、使用状态承接
- 商品浏览与兑换
- 积分展示与流水
- 分享赚积分入口
- 多语言切换
- 个人中心真实数据承接

#### 验收标准

- 页面不只是 UI 展示，而是前后端真实联通
- 关键按钮都有真实逻辑
- 关键状态都能查询与回显

---

### 模块五：多语言方案整改

#### 目标

严格按既定三语方案整改，不允许被简化成“三套模板手工录入”。

#### 原则

- 默认跟随设备 / 浏览器语言
- 支持手动切换中 / 泰 / 英
- 管理端与用户端逻辑一致
- 内容主录入可为一种语言
- 通过 AI 翻译生成其它语种备份
- 存储与调用逻辑统一

#### 验收标准

- 用户端主要页面实现中 / 泰 / 英切换
- 管理端主要页面实现中 / 泰 / 英切换
- 内容展示可按当前语言自动取值
- 不要求运营手工维护三套重复内容

---

### 模块六：A 系统旁路连接预留整改

#### 目标

当前阶段不强行做深度耦合，但要为后续与 A 系统真实联动预留数据结构与调用边界。

#### 原则

- 营销增长系统与 A 系统继续独立部署
- 旁路连接，不反向侵入 A 系统核心代码
- 通过入口、用户身份、设备、订单、活动承接等方式建立连接点

#### 当前需要预留的内容

- 用户标识映射位
- 设备编号 / 设备来源映射位
- 入口二维码映射位
- 来源渠道字段
- 与 A 系统交互的接口预留说明

#### 验收标准

- 当前系统结构不会阻碍后续旁路连接
- 关键对象已预留映射字段与接口边界
