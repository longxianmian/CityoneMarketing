# 问问 Agent 语义召回与卡片分发架构升级方案

## 一、文档定位

本文档只服务一件事：

**把 CityOne 用户侧数字服务助手“问问”，从“纯 LLM 分类 + 硬编码工具分发”升级为“语义召回 + 规则门控 + 工具分发 + 卡片编排 + 确认控制”的生产级架构。**

本文档不是宣传材料，也不是抽象概念说明。

本文档直接用于：

* 问问 Agent 架构升级
* 管理端配置能力开发
* pgvector 与意图向量库接入
* OSS 内容配置中心建设
* 卡片式分发链路开发
* Replit AI 或工程团队执行开发

---

## 二、为什么必须升级问问架构

问问当前已经具备以下基础：

* 已有 Agent 页面和基础骨架
* 已有基础 Skill 方向
* 已明确定位为用户侧数字服务助手
* 已明确要支持卡片式交互
* 已明确要支持积分、权益、会员、协议、优惠、站点、订单等服务场景

但如果继续沿用“关键词/分类器 + 硬编码工具分发”的方式，会持续出现这些问题：

| 现状问题                  | 根本原因                  |
| --------------------- | --------------------- |
| “今天有什么优惠”被拒绝或误判       | 关键词/分类器理解不足，表达覆盖不完整   |
| 新增服务需要改代码             | 意图逻辑、工具分发、页面内容硬编码在代码里 |
| 响应慢（5-15 秒）           | 两次串行 LLM 调用，先分类再生成    |
| 多语言覆盖不稳定              | 分类器对中/泰/英表达变体适应不够     |
| 问问虽要推卡片，但底层没有统一卡片分发链路 | 现有架构仍以文字问答为主          |

所以，问问不能继续做成“纯聊天式问答助手”，而必须升级为：

**语义召回与卡片分发引擎。**

---

## 三、升级后的目标

问问升级后的目标不是单纯“识别用户意图”，而是同时实现以下目标：

1. 更快判断用户问题是否属于问问能力范围
2. 更稳命中优惠、积分、会员、站点、订单、邀请等意图
3. 更自然地把结果分发为：

   * 文字回复
   * 页面入口卡片
   * 工具执行结果卡片
   * 确认卡片
   * 支付确认卡片
4. 降低对硬编码逻辑与多次 LLM 调用的依赖
5. 让新增意图、新增卡片、新增页面、新增规则可以通过后台和 OSS 配置扩展
6. 让问问真正具备“聊天界面里的任务入口与服务助手”能力

---

## 四、正确的新架构总览

```text
用户提问（中 / 泰 / 英）
        ↓
Embedding 向量化
        ↓
pgvector 意图召回（TopK=3）
        ↓
规则门控层（范围判断 + 风险判断 + 动作类型判断）
        ↓
命中结果分流
├── chat_only            → 直接一次 LLM 回复
├── card_only            → 直接推卡片
├── tool_then_card       → 调工具 → 推结果卡片 → LLM补一句自然话
├── tool_then_confirm    → 调工具 → 推确认卡片
├── tool_then_pay        → 调工具 → 推支付确认卡片
└── out_of_scope         → 返回拒绝语 / 转人工
```

### 核心改变

* 不再先用 LLM 分类，再用 LLM 生成
* 改为先用向量召回判断意图，再按动作类型分发
* LLM 在多数场景下降为一次调用
* 部分 out_of_scope 场景可零 LLM 调用
* 问问的核心不再是“聊天机器人”，而是“语义召回 + 工具分发 + 卡片编排”的服务引擎

---

## 五、为什么不能只做“相似度阈值命中/拒绝”

如果架构只有：

* 相似度 >= 阈值 → 命中
* 相似度 < 阈值 → 拒绝

会出问题。

### 原因

1. 优惠、积分、会员、活动、邀请等意图本身语义接近
2. 不同语言的相似度分布不一致
3. 用户一句话可能同时包含多个意图
4. 有些问题应推卡片，有些应查工具，有些应要求确认
5. 支付、兑换、权益变更不能只因相似度高就自动执行

所以必须有 **规则门控层**，统一判断：

* 是否在问问范围内
* 命中的意图类型
* 应采用哪种分发模式
* 是否需要确认
* 是否涉及支付
* 是否需要转人工

---

## 六、问问的分发模式定义（dispatch_mode）

问问必须至少支持以下 6 种分发模式。

### 6.1 chat_only

适用场景：

* 你好
* 你是谁
* 你能做什么
* 简单解释性问题

处理方式：

* 不调工具
* 直接一次 LLM 自然回复

### 6.2 card_only

适用场景：

* 有没有优惠
* 现在有什么活动
* 会员权益有哪些
* 查看规则入口

处理方式：

* 不一定调工具
* 直接推送对应卡片模板

### 6.3 tool_then_card

适用场景：

* 查询积分
* 查询可用优惠券
* 查询会员状态
* 查询附近站点
* 查询订单
* 查询活动资格

处理方式：

* 先调工具
* 再输出结果卡片
* LLM 补一句自然承接话

### 6.4 tool_then_confirm

适用场景：

* 领取权益
* 兑换积分权益
* 使用某项福利
* 更改会员状态

处理方式：

* 先调工具拿到结果
* 再推确认卡片
* 用户点击确认后方可继续

### 6.5 tool_then_pay

适用场景：

* 购买会员
* 下单支付
* 购买优惠商品
* 充值

处理方式：

* 先调工具准备订单/支付信息
* 再推支付确认卡片
* 必须由用户点击支付按钮继续

### 6.6 out_of_scope

适用场景：

* 明显超出问问边界的问题
* 与 CityOne 当前能力无关的问题

处理方式：

* 直接返回超出范围提示
* 必要时给出人工或其他入口
* 可零 LLM 调用

---

## 七、问问的范围边界

问问的服务边界必须清晰，不可无限扩张。

### 7.1 in_scope 范围

* 优惠/活动
* 卡券
* 积分
* 会员
* 协议与规则
* 邀请好友/分享赚积分
* 附近站点
* 借电帮助
* 支付帮助
* 订单/借还记录
* 用户权益说明

### 7.2 out_of_scope 范围

* 与 CityOne 无关的开放式百科问题
* 与当前业务无关的跨域任务
* 不属于问问职责范围的复杂事务

### 7.3 风险动作边界

以下动作不能由问问自动替用户完成：

* 支付
* 下单
* 会员购买
* 积分兑换确认
* 权益变更
* 重要授权确认

这些都必须通过：

* 确认卡片
* 支付确认卡片
* 用户主动点击按钮

来完成。

## 八、核心数据结构设计

## 8.1 intent_labels 表

问问的意图表不能只存：

* label_texts
* tool_name
* oss_page_key

这样不够支撑生产级问问。

### 建议字段

```text
id
intent_code
intent_name
label_texts
embedding
tool_name
oss_content_key
card_template_key
dispatch_mode
intent_scope
risk_level
requires_confirmation
requires_payment
priority
similarity_threshold
is_enabled
created_at
updated_at
```

### 字段说明

* **intent_code**：意图唯一标识
* **intent_name**：意图名称
* **label_texts**：中/泰/英多语言触发短语集合
* **embedding**：语义向量
* **tool_name**：命中后调用的工具，可为空
* **oss_content_key**：关联的 OSS 内容 key
* **card_template_key**：关联的卡片模板 key
* **dispatch_mode**：问问后续分发模式
* **intent_scope**：例如 in_scope / out_of_scope / greeting
* **risk_level**：风险等级
* **requires_confirmation**：是否需要确认卡片
* **requires_payment**：是否需要支付确认卡片
* **priority**：优先级
* **similarity_threshold**：该意图自己的命中阈值
* **is_enabled**：是否启用

---

## 8.2 推荐的初始意图

建议第一批至少录入以下意图：

| intent_code         | 意图名称       | tool_name               | dispatch_mode              |
| ------------------- | ---------- | ----------------------- | -------------------------- |
| intent_coupon       | 优惠/活动      | search_platform         | card_only 或 tool_then_card |
| intent_points       | 积分/兑换      | get_user_account        | tool_then_card             |
| intent_station      | 附近站点/借电点   | query_stations          | tool_then_card             |
| intent_invite       | 邀请好友/分享赚积分 | gen_invite_link         | tool_then_card             |
| intent_order        | 订单/借还记录    | get_user_orders         | tool_then_card             |
| intent_membership   | 会员权益       | null 或 get_user_account | card_only 或 tool_then_card |
| intent_policy       | 协议/规则      | null                    | card_only                  |
| intent_greeting     | 问候/能力介绍    | null                    | chat_only                  |
| intent_out_of_scope | 超出范围       | null                    | out_of_scope               |

## 九、OSS 的正确定位：内容配置中心，而不是纯页面文件存储

OSS 不能只存 pages/*.json。

问问真正需要的是 **内容配置中心**。

### 建议目录结构

```text
oss://cityone-growth/agent-content/
├── pages/
│   ├── coupons.json
│   ├── points.json
│   ├── stations.json
│   ├── invite.json
│   └── orders.json
├── cards/
│   ├── benefit_recommendation.json
│   ├── task_result.json
│   ├── growth_invite.json
│   ├── policy_info.json
│   ├── action_confirm.json
│   └── payment_confirm.json
├── policies/
│   ├── membership_terms.json
│   ├── points_rules.json
│   ├── user_agreement.json
│   └── privacy_policy.json
└── prompts/
    ├── greeting.json
    ├── out_of_scope.json
    └── transfer_to_manual.json
```

### 这意味着 OSS 将承载：

* 页面内容
* 卡片模板内容
* 协议规则内容
* 空态文案
* 拒绝语
* 转人工提示语
* 问候语与能力说明

### 升级价值

* 新增内容不必频繁改代码
* 运营可更新活动、规则、权益说明
* 问问能动态感知最新内容

## 十、细粒度意图建模补充

问问不能只把“优惠”当成一个粗意图，否则会把不同动作混在一起。

正确做法是：

**意图 = 主题域 + 动作 + 数据归属 + 分发模式**

### 10.1 为什么必须做细粒度意图建模

例如以下两句话虽然都与“优惠”相关，但动作意图不同：

1. **帮我看看我还有多少优惠券？**

   * 主题域：coupon
   * 动作：query_my_assets
   * 数据归属：user_private
   * 分发模式：tool_then_card

2. **我今天有什么优惠？**

   * 主题域：promotion
   * 动作：query_current_offers
   * 数据归属：platform_public
   * 分发模式：card_only 或 tool_then_card

如果只做“优惠”这个粗标签，会导致问问不知道该查用户自己的券包，还是推平台当前活动。

### 10.2 推荐的优惠主题域细粒度意图

| intent_code              | 意图说明     | dispatch_mode              | 说明           |
| ------------------------ | -------- | -------------------------- | ------------ |
| coupon_wallet_query      | 查询我的优惠券  | tool_then_card             | 查用户自己的券包     |
| platform_promotion_query | 查询平台当前优惠 | card_only / tool_then_card | 查平台公共优惠活动    |
| coupon_claim_intent      | 领取优惠券    | tool_then_confirm          | 先查可领资格，再确认领取 |
| coupon_usage_help        | 优惠券怎么用   | chat_only / card_only      | 说明使用方式或推规则卡片 |
| coupon_rule_query        | 优惠券规则    | card_only                  | 推规则说明卡片      |

## 十一、问问完整请求流程示例

## 10.1 场景一：用户问“今天有什么优惠？”

### 输入

用户：**今天有什么优惠？**

### 处理流程

1. Embedding 向量化
2. pgvector 检索 TopK 意图
3. Top1 命中 `intent_coupon`
4. 相似度达到该意图阈值
5. 规则门控判定：in_scope
6. dispatch_mode = `card_only` 或 `tool_then_card`
7. 读取对应 OSS 内容和卡片模板
8. 返回优惠推荐卡片
9. 需要时补一句自然语言承接
10. 若适合裂变，再补分享赚积分卡片

### 输出形态

* 文字承接一句
* 优惠推荐卡片
* 可选：裂变引导卡片

---

## 10.2 场景二：用户问“我的积分还有多少？”

### 输入

用户：**我的积分还有多少？**

### 处理流程

1. Embedding 向量化
2. TopK 检索命中 `intent_points`
3. dispatch_mode = `tool_then_card`
4. 调用 `get_user_account`
5. 读取结果
6. 组装任务结果卡片
7. LLM 生成一句自然语言回复
8. 可补积分兑换入口卡片

### 输出形态

* 文字承接一句
* 任务结果卡片
* 可选：积分兑换入口卡片

---

## 10.3 场景三：用户发起购买/支付类动作

### 输入

用户：**帮我开会员**

### 处理流程

1. Embedding 向量化
2. 命中 `intent_membership`
3. dispatch_mode = `tool_then_pay`
4. 工具准备订单或支付信息
5. 生成支付确认卡片
6. 由用户点击“去支付”按钮继续

### 输出形态

* 支付确认卡片
* 不允许问问自动支付

---

## 11.4 场景四：用户提问超出范围

### 输入

用户：**帮我订机票**

### 处理流程

1. Embedding 向量化
2. Top1/TopK 相似度不足
3. 规则门控层判定 = out_of_scope
4. 直接返回超出范围提示
5. 必要时给出人工入口或服务边界说明

### 输出形态

* 简短拒绝语
* 可选：人工入口提示
* 可零 LLM 调用

---

## 11.5 场景五：用户说“帮我领取优惠券”

### 这类场景的本质

“帮我领取优惠券”不是普通问答，也不是单纯查询，而是：

* 涉及用户权益变化
* 属于领取动作
* 不能由问问直接自动执行
* 必须走：**先查可领资格/可领列表 → 再推确认卡片 → 用户确认后执行**

### 对应细粒度意图

```json
{
  "intent_code": "coupon_claim_intent",
  "domain": "coupon",
  "action": "claim_coupon",
  "data_scope": "platform_to_user",
  "dispatch_mode": "tool_then_confirm",
  "requires_confirmation": true,
  "requires_payment": false
}
```

### 处理流程

1. Embedding 向量化
2. 命中 `coupon_claim_intent`
3. dispatch_mode = `tool_then_confirm`
4. 调用 `get_claimable_coupons` 查询当前用户可领取的优惠券列表、资格、限制条件、有效期
5. 根据结果分情况处理：

   * 若只有 1 张可领券：直接推确认卡片
   * 若有多张可领券：先推可领取列表卡片，用户选定后再推确认卡片
   * 若没有可领券：返回无可领取结果，并可顺势推当前活动卡片或分享赚积分卡片
6. 用户点击确认后，才调用 `claim_coupon_with_confirmation`
7. 返回领取成功结果卡片

### 输出形态

#### 情况 A：只有 1 张可领取优惠券

* 先一句承接语
* 再推确认卡片

#### 情况 B：有多张可领取优惠券

* 先一句承接语
* 再推可领取列表卡片
* 用户选择后，再推确认卡片

#### 情况 C：没有可领取优惠券

* 返回无可领取提示
* 可补充当前活动卡片
* 可补充“分享权益给朋友，你也能获得积分”的裂变引导卡片

### 这一场景需要的 Skill

```json
[
  {
    "name": "get_claimable_coupons",
    "description": "查询当前用户可领取的优惠券列表、资格、限制条件与有效期。"
  },
  {
    "name": "claim_coupon_with_confirmation",
    "description": "在用户点击确认后执行优惠券领取动作，并返回领取结果。"
  }
]
```

### 关键原则

* 问问不能听到“帮我领取优惠券”就直接执行
* 必须先查可领资格与列表
* 必须由用户确认后再领取
* 这类动作属于权益变化动作，不可自动越权完成

## 十二、问问支持的卡片体系

问问不是纯文字助手，而是卡片式服务与任务执行助手。

### 11.1 优惠推荐卡片

用于：

* 有没有优惠
* 有什么活动
* 现在有什么福利

### 11.2 任务结果卡片

用于：

* 查询积分
* 查询优惠券
* 查询会员状态
* 查询订单
* 查询站点

### 11.3 裂变引导卡片

用于：

* 用户表现出“想省钱/想免费体验”意图
* 柔性引导其分享权益给朋友，同时自己获得积分

### 11.4 规则说明卡片

用于：

* 会员条款
* 积分规则
* 用户协议
* 隐私政策
* 服务条款

### 11.5 确认操作卡片

用于：

* 领取权益
* 兑换积分权益
* 更改状态

### 11.6 支付确认卡片

用于：

* 支付
* 开会员
* 下单
* 充值

## 十二、后台必须提供的能力

问问升级后，后台不能只是配置 Agent 基本信息，必须补这几项核心能力。

## 12.1 意图管理

支持：

* 新增/编辑/删除意图
* 管理多语言 label_texts
* 管理 tool_name
* 管理 dispatch_mode
* 管理 threshold
* 管理 card_template_key
* 启用/停用

## 12.2 重新 Embedding 按钮

当以下内容被修改后，必须支持重新生成 embedding：

* label_texts
* 多语言表达
* 意图说明

否则新意图不会真正生效。

## 12.3 召回测试台

后台必须允许输入一条测试语句，例如：

* 今天有什么优惠
* ลดราคาไหม
* where is the nearest station

系统应返回：

* Top1 / Top3 命中意图
* similarity 分数
* tool_name
* dispatch_mode
* 是否需要确认
* card_template_key

这个能力非常重要，否则后台调意图属于盲调。

## 12.4 卡片模板管理

支持：

* 新增/编辑/删除卡片模板
* 多语言内容管理
* 预览
* 绑定意图
* 绑定页面入口
* 绑定按钮与 payload

## 12.5 OSS 内容配置管理

至少支持：

* 关联 OSS key
* 查看对应配置状态
* 内容同步状态
* 内容未配置占位提示

## 十三、与现有系统的兼容原则

问问本次升级必须坚持以下原则：

1. **不推翻现有问问页面骨架重做**
2. **不大改现有 AgentChatPage 主结构**
3. **现有工具接口尽量保留，不推倒重来**
4. **以增量改造为主，不另起一套新系统**
5. **数据库只新增必要表与字段，不破坏现有主流程**
6. **先做配置中心，再做召回链路，再做生产级优化**

## 十五、最终结论

问问不能继续做成“纯文字客服”或“纯 LLM 分类器”。

问问正确的未来形态应当是：

**语义召回 + 规则门控 + 工具分发 + 卡片编排 + 确认控制** 的数字服务与任务入口引擎。

必须坚持以下结论：

1. 问问不是普通聊天机器人，而是卡片式服务与任务助手
2. 问问必须支持页面入口卡片、结果卡片、裂变卡片、规则卡片、确认卡片、支付确认卡片
3. 问问的意图识别不能继续依赖纯关键词或纯硬编码逻辑
4. 意图库、卡片模板、规则内容、页面内容都必须配置化
5. 支付、兑换、权益变更必须由用户点击确认，不得自动执行
6. 现有系统应走增量改造路线，不得推翻重做
7. 这套架构比当前方式更快、更稳、更容易扩展，也更符合 CityOne 的长期运营目标
