# CityOne 营销增长系统第二批第1份：认证与账户体系整改执行文档

> 适用范围：CityOne → 营销增长系统生产级整改 → 第二批第 1 份执行任务
>
> 本文档只处理认证与账户体系，不允许扩散到其它模块。
>
> 本次整改范围仅限：
>
> * `auth/admins`
> * `members`
> * `accounts`
>
> 本文档用于直接分发给 ReplitAI 执行。

---

## 一、整改背景

第一批 PostgreSQL 迁移已完成并验证通过，当前已完成：

* DB 连接池 + 自动迁移
* 001_core_business.sql 已建核心业务表
* coupons.js 已完成 CRUD 与 JSONB 双格式修复
* mall-items.js 已完成 CRUD 与 OSS 图片承接
* growth-points.js 已完成积分账户 / 积分账本 / 调整 / 兑换原子事务
* 历史 JSON 数据 seed 已完成第一批核心数据入库
* 前端已验证可正常渲染数据库数据
* API E2E 测试已通过
* 生产连接方案已确认，只需切换正式 DATABASE_URL 即可对接阿里云 RDS

当前第二批仍有约 35 个 JSON 文件未迁移，其中最优先的不是 agent，也不是配置杂项，而是认证与账户体系。

原因：

1. 管理端登录与权限必须先稳定落库
2. 用户账户与会员身份是活动、积分、订单、分享归因的基础
3. 后续入口归因、活动参与、A 系统旁路连接都依赖正式账户体系
4. 如果 auth/admins、members、accounts 继续停留在 JSON，后续模块整改会持续返工

---

## 二、整改目标

本次目标是把当前营销增长系统中的认证与账户体系，从 JSON 存储整改为 PostgreSQL 正式存储，并完成真实接口读写承接。

整改完成后，至少应实现：

### 1. 管理员体系正式落库

* 管理员账号不再依赖 JSON 文件
* 管理员登录、查询、状态变更可走 PostgreSQL
* 权限、角色、启停状态、最后登录时间等基础字段具备正式承接能力

### 2. 会员体系正式落库

* 会员基本资料、身份、状态、标签等具备正式表结构
* 与积分账户、订单、活动参与具备后续关联基础
* 不再依赖 JSON 文件承接会员信息

### 3. 账户体系正式落库

* 账户对象与会员对象关系清晰
* 登录标识、来源、绑定信息、渠道信息具备正式结构
* 为未来接入 A 系统用户映射预留字段

### 4. 认证相关接口真实读写

* 至少一条管理员登录链路完成 PostgreSQL 读写承接
* 至少一条会员/账户查询链路完成 PostgreSQL 承接
* 不允许页面继续只是“假接口 + JSON 文件”

---

## 三、本次整改范围（严格限定）

你这次只能处理以下 3 类模块：

### 1. `auth/admins`

重点关注：

* 管理员登录
* 管理员列表
* 管理员创建/编辑/启停
* 密码存储与校验
* 角色/权限基础字段
* 最后登录时间

### 2. `members`

重点关注：

* 会员资料
* 会员状态
* 会员标签/身份字段
* 会员与积分/订单/活动参与的后续关联主键基础

### 3. `accounts`

重点关注：

* 账户唯一标识
* 账户类型
* 登录标识（手机号 / 邮箱 / LINE / 内部 ID / 其它真实字段）
* 渠道来源
* 第三方绑定预留
* 与 member 的一对一或一对多关系

### 本次明确不处理

以下内容这次先不要动：

* `activities`
* `entries`
* `landing`
* `banners`
* `stations`
* `game-programs`
* `messages`
* `biz-*`
* `agent-*`

## 四、必须先做的真实代码检查

你不能先猜表结构，必须先基于真实代码检查当前实现。

### 先检查并反馈以下内容

#### 1）真实文件位置

必须找到以下真实文件：

* `auth/admins` 对应的 routes / services / data 文件
* `members` 对应的 routes / services / data 文件
* `accounts` 对应的 routes / services / data 文件
* 当前 JSON 文件存储目录
* 当前后端使用的类型定义 / DTO / schema 文件
* 当前登录鉴权相关中间件或工具文件

#### 2）当前数据来源方式

必须确认：

* 这 3 类模块当前是不是都还在读 JSON
* 是否存在一部分已走 PostgreSQL、一部分仍走 JSON 的混合状态
* 哪些接口已经是真读写，哪些只是读静态数据

#### 3）当前字段真实情况

必须梳理每类对象当前真实字段：

* 字段名
* 当前来源（JSON / mock / DB）
* 是否被前端真实使用
* 是否需要保留
* 是否需要重命名或规范化

#### 4）当前登录链路

必须确认：

* 管理员登录是怎么校验的
* 密码是否已哈希
* token / session / cookie / jwt 如何处理
* 登录成功后返回哪些字段
* 当前是否写入 last_login_at 或登录日志

### 先输出检查结论，再开始改

你必须先给出一份简短检查结论，至少包含：

1. 找到了哪些真实文件
2. 这 3 类模块当前分别是如何存储的
3. 当前登录与鉴权机制是什么
4. 建议如何设计正式表结构与迁移路径

## 六、整改实施要求

### 第一阶段：迁移设计

你需要完成：

1. 为 `admins`、`members`、`accounts` 设计正式 PostgreSQL 表结构
2. 输出 migration / schema 变更
3. 明确 JSON → PostgreSQL 的迁移策略
4. 明确哪些历史字段保留、哪些废弃、哪些需兼容

### 第二阶段：历史 JSON 数据迁移

你需要：

1. 找到当前对应 JSON 文件
2. 设计迁移脚本或 seed 脚本
3. 将历史管理员、会员、账户数据导入 PostgreSQL
4. 对脏数据、空字段、重复键给出处理方式

### 第三阶段：接口读写切换

你需要：

1. 将相关 routes / services / repository 改为优先走 PostgreSQL
2. 移除或降级对 JSON 文件的主依赖
3. 保证管理员登录链路走 PostgreSQL 校验
4. 保证管理员列表、会员查询、账户查询至少一批核心接口已切换到 DB

### 第四阶段：兼容与稳定性处理

你需要：

1. 保证旧前端页面在字段不崩的前提下完成切换
2. 对缺失字段做兼容处理
3. 如果密码历史明文/旧格式存在，必须说明兼容迁移策略
4. 不允许因为迁移导致管理端无法登录

## 七、必须覆盖的功能验证

整改完成后，至少要完成以下验证。

### A. 管理员体系验证

1. 管理员登录成功
2. 管理员密码校验成功
3. 管理员列表返回 PostgreSQL 数据
4. 管理员启停状态能读写
5. 最后登录时间如有逻辑，应正确更新

### B. 会员体系验证

1. 会员列表或会员详情能从 PostgreSQL 返回
2. 会员关键字段可正确渲染
3. 与积分账户关联主键保持可用

### C. 账户体系验证

1. 账户列表或账户详情能从 PostgreSQL 返回
2. 账户与 member 的关联关系正常
3. 账户来源/绑定字段至少可查

### D. 迁移验证

1. JSON 原有数据已成功导入 PostgreSQL
2. 数量对账基本一致
3. 抽样核对字段正确
4. 至少输出迁移前后数量对比
