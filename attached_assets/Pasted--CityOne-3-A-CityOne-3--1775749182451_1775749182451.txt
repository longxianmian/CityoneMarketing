## 二、整改目标

本次整改目标是把当前 `stations` 模块从 JSON / 假数据 / 缺结构状态，整改为 PostgreSQL 正式承接，并完成“站点—设备—入口—活动”之间的第一版关系预留。

整改完成后，至少应实现：

### 1. 站点体系正式落库

* 站点不再依赖 JSON 文件
* 站点基本信息、状态、位置、渠道归属、入口绑定具备正式表结构
* 后续可承接商场、餐厅、学校、品牌点位等线下场景

### 2. 设备映射预留正式落库

* 站点下可预留设备编号/设备组字段
* 为后续 A 系统设备编号映射预留结构
* 当前不强做实时联动，但必须保证字段与关系可扩展

### 3. 入口二维码与站点绑定预留

* 入口实例可反查所属站点
* 站点可反查对应入口/二维码
* 为“站点二维码 → 增长系统入口 → 活动承接”建立正式关系基础

### 4. A 系统旁路连接映射位预留

至少预留以下维度：

* `a_system_station_id`
* `a_system_device_id`
* `a_system_user_id`（如适合）
* `device_code`
* `station_code`
* `entry_code`

### 5. 第一版站点归因基础

至少形成以下可追溯关系：

* 某个 `station`
* 绑定哪个 `entry`
* 关联哪个 `landing`
* 默认承接哪个 `activity`
* 预留哪个 `device_code / a_system_device_id`

## 五、建议数据模型（先基于真实代码校对再落地）

以下是建议方向，不允许脱离现有代码强造。你必须先与真实字段对齐，再决定最终建表方案。

### 方案优先级建议

优先评估两种方案：

#### 方案 A：先单表承接（推荐起步）

先以 `stations` 主表承接核心字段，设备相关先做预留字段，不立刻拆独立 `station_devices` 表。

适用条件：

* 当前项目设备关系还未稳定
* 当前只需要先把站点与入口、活动、A 系统映射位建立起来
* 目标是最小可用生产结构

#### 方案 B：站点表 + 设备表

如果真实代码里已经明显存在“一站多设备”的稳定模型，且前端/业务已强依赖设备粒度，则评估：

* `stations`
* `station_devices`

但不能凭空为了“看起来高级”强拆。

### 1. stations（站点表）建议字段

至少评估以下字段：

* `entry_id`
* `entry_code`

* `device_code`（预留）

### 2. station_devices（如确有必要才建）建议字段

## 六、整改实施要求

### 第一阶段：迁移设计

你需要完成：

1. 为 `stations` 设计正式 PostgreSQL 表结构
2. 如确有必要，再评估是否增设 `station_devices`
3. 输出 migration / schema 变更
4. 明确 JSON → PostgreSQL 的迁移策略
5. 明确哪些历史字段保留、哪些废弃、哪些兼容

### 第二阶段：历史 JSON 数据迁移

你需要：

1. 找到当前对应 JSON 文件
2. 设计迁移脚本或 seed 脚本
3. 将历史站点数据导入 PostgreSQL
4. 对脏数据、空字段、重复键给出处理方式

### 第三阶段：接口读写切换

你需要：

1. 将 `stations` 相关 routes / services / repository 改为优先走 PostgreSQL
2. 移除或降级对 JSON 文件的主依赖
3. 保证站点列表 / 站点详情 / 站点启停等核心接口走 PostgreSQL
4. 至少完成一条站点 → entry / landing / activity 的查询链路

### 第四阶段：A 系统旁路连接预留

你需要：

1. 补齐与 A 系统旁路连接有关的预留字段
2. 不要求立即真实对接 A 系统接口
3. 但必须能清晰表达后续连接点在哪里
4. 若已有 user / member 表中的 `a_system_user_id` 预留，请保证命名体系一致

### 第五阶段：前端兼容承接

你需要：

1. 保证现有站点相关页面字段不崩
2. 对缺失字段做兼容处理
3. 不允许因为迁移导致站点页或配置页白屏
