# CityOne AI Agent 后端开发技术文档（基于当前增长系统源码整理）

## 一、文档定位

本文档基于你上传的 **cityone-growth-backend 最新源码** 整理，目标不是重新发明一套新后端，而是：

1. 以当前后端真实结构为基础扩展 AI Agent。
2. 保持与现有“入口分流 / OA 关注 / A 系统旁路桥接 / 活动路由”架构一致。
3. 支持 **OA 粉丝、真实用户、会员** 三层身份的自然语言代理能力。
4. 为前端用户端 AI 聊天页、前端管理端 Agent 管理中心提供可直接开发的接口与模块设计。

---

## 二、当前后端源码真实情况

### 1）当前技术栈

从源码可确认：

* 运行方式：`node src/index.js`
* 模块规范：ESM（`"type": "module"`）
* HTTP 层：Node 原生 `http`
* 上传：`busboy`
* 数据持久化：当前版本以 `data/*.json` 文件为主，不是数据库版
* 路由组织：在 `src/index.js` 中集中注册
* 现有业务重心：

  * 入口解析 `entry`
  * 路由规则 `routes`
  * 入口模板/实例 `entries`
  * 落地页/活动/商品
  * 奖池、刮刮卡、转盘、签文等互动能力
  * OA 回流、A 系统桥接、自动注册、事件埋点

### 3）当前系统已有、可直接复用的能力

这是做 AI Agent 最关键的基础，不需要推翻重做：

#### A. 入口与身份分流能力已经存在

`entry-resolver.js` 已经具备：

* 入口类型识别
* 用户阶段识别
* 是否需要先关注 OA 的分流判断
* 非业务活动入口与业务借电入口分流
* A 系统桥接上下文生成
* 自动注册上下文生成
* 奖励计划与事件埋点上下文生成

这意味着：

**AI Agent 完全可以复用“用户阶段识别 + A 系统业务上下文 + OA 约束”这一套现有机制。**

#### B. A 系统桥接能力已经存在雏形

`a-system-bridge.js`、`a-system-live-provider.js`、`a-system-mock-provider.js` 已经定义了：

* mock / live 两种桥接模式
* 押金状态、首借状态、借电可用性等业务判断位
* 根据桥接结果给出建议动作

这意味着 Agent 不需要直接写死共享充电宝逻辑，而是应该：

**通过 Agent Tool 层统一调 A 系统桥接层。**

#### C. OA 回流能力已经存在雏形

`oa-router.js` 已有：

* OA 跳转地址生成
* 回流路径拼装
* follow return token 生成

这意味着 Agent 可天然支持：

* 未关注 OA 用户先引导关注
* 关注后回流继续执行之前任务

#### D. 事件埋点能力已经存在雏形

`event-tracker.js` 已有：

* `entry_opened`
* `oa_follow_required`
* `oa_auto_registered`
* `business_routed / feature_routed`

这意味着后续可扩展为：

* AI 对话事件
* Agent 意图识别事件
* Agent 工具执行事件
* Agent 转化结果事件

## 三、当前后端缺口判断

基于源码查看，当前版本 **还没有真正的 AI Agent 后端**，用户端 `AgentChatPage.tsx` 目前仍是前端本地 mock 回复。

也就是说，后端当前缺的是以下 6 个核心模块：

1. Agent 会话接口层
2. Agent 意图识别层
3. Agent 工具路由层
4. Agent 权限分层层
5. Agent 执行日志与追踪层
6. Agent 管理配置层

所以本次开发的目标，不是改造现有 entry 系统，而是：

**在现有增长系统后端上，新增一条 AI Agent 业务主线。**

---

## 四、后端总体设计原则

### 原则 1：Agent 必须是“可执行代理”，不是纯问答机器人

后端不能只返回一段文本，而要支持：

* 查询类动作
* 推荐类动作
* 领券/报名/锁券类动作
* 工单类动作
* 需要二次确认的代理动作

### 原则 2：Agent 不能绕开 OA / 用户 / 会员身份分层

身份分层必须成为后端权限基石：

* OA 粉丝：轻代理
* 已使用用户：中代理
* 会员：强代理

### 原则 3：Agent 必须走“白名单意图 + 工具调用”模式

第一阶段不要直接做开放式 LLM 自由调用，避免跑偏。

### 原则 4：Agent 必须复用当前 entry / A-system / OA 的现有能力

不要另起炉灶做一套新的身份判断和业务桥。

### 原则 5：所有执行型操作必须可追溯

每次意图识别、工具调用、执行结果都要记录。

## 六、后端能力分层设计

# 1. Agent 会话层

### 目标

负责用户进入聊天页后的会话创建、历史消息保存、上下文归并。

### 建议新增接口

#### `POST /api/agent/session/init`

作用：初始化会话，返回当前用户身份、可用能力、欢迎语、快捷问题。

请求示例：

```json
{
  "line_user_id": "u_xxx",
  "site_id": "site_001",
  "entry_type": "device_qr",
  "entry_code": "D001",
  "language": "zh"
}
```

返回示例：

```json
{
  "code": 200,
  "msg": "agent session initialized",
  "data": {
    "session_id": "as_001",
    "identity_tier": "oa_fan",
    "identity_label": "已关注 OA 粉丝",
    "member_level": "fan",
    "capabilities": [
      "borrow_help",
      "coupon_help",
      "points_help",
      "invite_help"
    ],
    "quick_prompts": [
      "帮我找附近站点",
      "帮我看看有哪些券能用",
      "积分怎么兑换？",
      "如何邀请好友？"
    ],
    "welcome_message": "你好，我是 CityOne AI 助理。"
  }
}
```

#### `GET /api/agent/session/:sessionId/messages`

作用：获取历史消息。

#### `POST /api/agent/session/:sessionId/message`

作用：发送用户消息，由后端统一识别意图并返回结构化结果。

# 2. Agent 身份识别层

### 目标

基于当前已有 `entry-resolver + identity-register + a-system-bridge` 结果，统一生成 Agent 的权限身份。

### 推荐身份分层

#### A. `guest_unfollowed`

* 未关注 OA
* 仅允许说明型问答
* 不允许执行型动作

#### B. `oa_fan`

* 已关注 OA
* 允许 FAQ、站点查询、活动说明、福利说明
* 可做轻度代理

#### C. `identified_user`

* 已真实使用过或可识别真实业务身份
* 允许订单、卡券、积分、活动资格查询
* 可做中度代理

#### D. `member`

* 已押金且至少完成一次消费，或后续定义的会员用户
* 允许强代理能力
* 但支付/退款/押金动作仍需二次确认

### 实现建议

新增 `agent-identity-service.js`：

* 输入：`line_user_id / user_id / site_id / entry params`
* 输出：

  * `identity_tier`
  * `user_stage`
  * `deposit_status`
  * `first_borrow_status`
  * `borrow_availability`
  * `available_tools`
  * `blocked_tools`

### 关键点

当前 `entry-resolver.js` 返回的：

* `user_context`
* `diversion_context`
* `business_context`
* `borrow_decision`

这四块要直接复用于 Agent 身份识别，不要重复造轮子。

---

# 3. Agent 意图识别层

### 目标

把自然语言转成 **白名单意图 + 槽位参数**。

### P0 阶段意图白名单建议

建议首批只支持 12 个意图：

1. `nearby_sites_query` 查附近站点
2. `borrow_help` 借电流程说明
3. `return_help` 还电流程说明
4. `coupon_list_query` 查我的可用券
5. `coupon_recommend` 推荐最优券
6. `benefit_claim_query` 查我还能领什么福利
7. `points_balance_query` 查积分
8. `points_redeem_help` 积分兑换说明
9. `invite_help` 邀请说明
10. `invite_poster_generate` 生成邀请海报
11. `recent_orders_query` 查最近订单
12. `after_sale_apply` 发起售后

### 建议实现方式

P0 先不用重 LLM，可先做：

* 关键词词典
* 正则匹配
* 短语归一化
* 语言别名表（中/泰/英）

例如：

```json
{
  "intent_code": "coupon_recommend",
  "phrases": {
    "zh": ["最划算的券", "推荐优惠券", "我能用什么券"],
    "th": ["คูปองที่คุ้มที่สุด", "แนะนำคูปอง", "ใช้คูปองอะไรได้"],
    "en": ["best coupon", "recommend coupon", "what coupon can I use"]
  }
}
```

### 返回结构建议

```json
{
  "intent_code": "coupon_recommend",
  "intent_name": "推荐最优券",
  "confidence": 0.92,
  "slots": {
    "site_id": "site_001",
    "entry_code": "D001"
  },
  "need_confirm": false
}
```

# 4. Agent 权限策略层

### 目标

判断当前身份是否允许执行某意图。

### 建议新增 `agent-policy-service.js`

核心职责：

* 根据 `identity_tier + intent_code` 判定是否可执行
* 给出 `allowed / blocked / need_follow / need_upgrade / need_confirm`

### 策略矩阵建议

#### 未关注 OA

允许：

* `borrow_help`
* `return_help`
* `invite_help`
* `points_redeem_help`

禁止：

* 查本人卡券
* 查本人订单
* 领本人福利
* 生成个人邀请海报

#### OA 粉丝

允许：

* FAQ
* 查福利
* 查附近站点
* 活动说明
* 生成基础邀请链接/海报

#### 已识别用户

允许：

* 查券
* 查订单
* 查积分
* 领活动福利
* 推荐最优券

#### 会员

允许：

* 强代理动作
* 复杂权益推荐
* 借电前准备型动作
* 售后代理提交

### 目标

把工具结果转成用户端可展示的结构化消息。

### 不建议只返回纯文本

建议统一返回：

```json

  "text": "我帮你找到了当前最划算的券。",
  "cards": [

      "card_type": "coupon",

      "desc": "当前站点可用，优先级最高",
      "action_text": "立即去使用",
```

## 九、与现有后端模块的对接关系

# 1. 与 Entry 体系的关系

AI Agent 不是替代入口分流，而是：

* 用户进入 `/agent` 或 `/agent/chat` 后
* 可带上 `site_id / entry_type / entry_code`
* Agent 后端使用 `entry-resolver` 获得当前业务上下文
* 再根据上下文做个性化代理能力

也就是说：

**Entry 是流量入口中枢，Agent 是自然语言操作中枢。**

---

# 2. 与 OA 体系的关系

未关注 OA 用户：

* 可咨询
* 但执行型动作受限
* 需要通过 `oa-router.js` 生成关注跳转与回流继续处理

这部分必须做成标准能力，而不是写死在前端。

---

# 3. 与 A 系统旁路桥的关系

Agent 需要查询的业务能力，大部分最终都要落到 A 系统或未来正式用户中心：

* 借电状态
* 首借状态
* 押金状态
* 最近订单
* 设备站点可用性

当前建议：

* P0 先通过 `a-system-bridge.js` 走 mock/live 两态
* P1 再逐步补真实查询接口

## 十、P0 阶段建议先落地的后端工具

建议不要一次性全做，先做 6 个最值钱工具：

### 1）`tool-nearby-sites.js`

* 输入：站点/定位/入口上下文
* 输出：附近站点列表
* 当前可先 mock，后续接 A 系统站点服务

### 2）`tool-coupon-list.js`

* 输出：当前用户可用券
* 当前可先走本系统活动/卡券数据

### 3）`tool-coupon-recommend.js`

* 结合站点/身份/活动，推荐最优券

### 4）`tool-claim-benefits.js`

* 查询用户还可领取的福利
* 可联动活动、首借奖励、关注奖励

### 5）`tool-invite-poster.js`

* 生成个人邀请链接/海报描述数据
* 先返回分享文案 + 分享链接，海报图像后续增强

### 6）`tool-order-query.js`

* 查最近订单
* 后续对接 A 系统真实订单

### 各文件职责

## 十三、风控与边界要求

### 1）以下动作必须二次确认

* 提交兑换
* 发起售后

## 十四、给后端开发的最终结论

基于当前源码，最正确的做法不是新起一套 AI 服务，而是：

**在现有增长系统后端内，新增一条 Agent 主线，并复用现有 entry / OA / A 系统桥接能力。**

后端的核心落点是 5 件事：

1. 会话初始化
2. 身份分层
3. 意图白名单识别
4. 工具路由执行
5. 结构化回复与日志留痕

这样做的好处是：

* 不会偏离你们当前营销增长系统主架构
* 能和 OA 关注、首借、押金、会员、活动转化天然联动
* 后续也容易把 Agent 做成增长转化中枢，而不是单纯客服机器人
