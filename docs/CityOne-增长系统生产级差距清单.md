# CityOne 增长系统生产级差距清单

更新日期：2026-04-16

## 1. 当前结论

截至 2026-04-16，CityOne 增长系统尚未达到“全系统生产级运行标准”。

更准确地说：

- 福利中心主链路已经具备生产化基础，尤其是活动、卡券、权益、积分、问问 Agent 的基础骨架已经成型。
- 但归因、客户主数据、站点福利承接、环境稳定性、外部系统对接一致性还没有形成完整的生产级闭环。
- 当前系统状态更适合定义为：
  - 核心增长链路：接近生产级
  - 全系统治理与数据闭环：未达生产级

## 3. 已接近生产级的部分

### 3.1 活动主链路

已具备以下能力：

- 活动创建、编辑、发布
- 发布前奖励校验
- 活动参与落库
- 参与后发放积分
- 参与后自动发放奖励券
- 奖励券与活动绑定关系可追溯

当前判断：

- 结构上已经从“演示页面”进入“正式业务链路”
- 仍需补更完整的异常审计和运营验收

### 3.2 卡券与权益主链路

已完成的关键收口：

- 已拥有券与待领取券分离
- 已拥有券不会再误走 claim
- 权益动作支持按类型分流
- 商品兑换券已支持绑定具体商品
- 绑定商品存在删除/下架保护

当前判断：

- 这部分已经摆脱“逻辑混乱期”
- 适合继续做生产级完善，而不是推倒重来

### 3.3 问问 Agent 骨架

已有能力：

- Agent 配置中心
- 意图管理
- 意图命中测试器
- 工具管理
- 会话日志
- 指标看板
- 问问运行时身份识别、规则门控、工具分发、卡片编排骨架

当前判断：

- 已经不是纯概念页
- 但还没有到“高可信、强权限、可审计自动执行”的生产级 Agent

## 4. 尚未达到生产级的核心缺口

### 4.1 归因体系未形成统一闭环

这是当前最大的生产级风险之一。

现状：

- 系统存在入口解析、事件上下文、店员归因、来源绑定等服务骨架
- 但漏斗归因、订单归因、来源对象、站点对象、活动对象之间还没有统一口径
- 管理端存在明确占位页，说明该链路尚未真正完成

表现：

- “转化漏斗”仍是占位能力
- “订单归因”仍是占位能力
- 归因中心前端存在部分未落地的后端接口依赖

生产级风险：

- 无法稳定回答“某用户/订单/活动参与到底归因给谁”
- 无法形成可信运营复盘
- 无法形成财务或奖励发放对账基础

### 4.2 客户管理不是客户主数据中心

现状：

- 客户管理页已可展示粉丝、用户、会员三层视图
- 但其定义仍偏运营视角，不是全系统统一主数据口径
- 来源字段和权益字段仍有“后续对接真实数据”的提示

生产级风险：

- 同一个用户在不同模块的身份定义可能不一致
- 会员、用户、粉丝、权益、订单、积分之间缺统一主键和统一解释口径

### 4.3 站点福利仍是承接视图，不是正式编排结果页

现状：

- 站点管理基础数据已可维护
- 站点福利页目前仍主要复用站点管理页的只读视图
- 尚未形成“站点命中的活动/卡券/入口/默认展示”的正式汇总页

生产级风险：

- 运营无法快速确认某站点用户到底会看到什么
- 无法清晰排查“该站点为什么没展示某活动/某券”

### 4.4 商品/实物奖励尚未完成生产验收

现状：

- 商品兑换券到商品绑定已经打通
- 兑换记录和配送字段已有基础支持

但仍缺：

- 库存约束的完整压测
- 实物配送与状态流转验收
- 售后/取消/退款逻辑
- 核销/履约全链路回查

生产级风险：

- 一旦放量，会在库存和履约环节暴露问题

### 4.5 环境稳定性未达到生产标准

现状：

- 本地前端可运行
- 本地后端可启动
- 但本地无法直连远端 PostgreSQL
- 本地 pgvector 与真实向量能力不具备稳定运行条件
- 当前意图命中测试器依赖本地兜底模式

生产级风险：

- 开发、测试、生产环境口径不一致
- 本地验证通过不等于真实环境验证通过

## 5. 当前最重要的生产级风险

### P0：数据口径不统一

典型对象：

- 用户
- 站点
- 活动
- 卡券
- 权益
- 来源
- 订单

风险说明：

- 如果这些对象没有统一定义，系统规模一上来就会出现统计打架、归因打架、页面展示打架

### P0：归因链路不可审计

风险说明：

- 无法稳定回溯“入口 -> 关注 -> 注册/识别 -> 活动参与 -> 发券/发积分 -> 借电/订单”
- 无法判断奖励发放是否合理

### P1：页面已成型，但部分后端闭环不足

风险说明：

- 容易出现“看起来像生产系统，实际上只是半成品”的错觉

### P1：外部系统依赖未收口

涉及：

- A 系统
- RDS 网络
- pgvector
- LLM/Embedding 依赖

风险说明：

- 本地、测试、正式环境表现不一致

## 6. 必补项清单

### 6.1 数据地图

必须补一版全系统数据地图，至少明确这些对象：

- 用户
- LINE 粉丝身份
- 会员身份
- 站点
- 入口
- 渠道
- 活动
- 卡券
- 用户券
- 积分账户
- 积分流水
- 商品
- 兑换单
- 订单
- Agent 会话
- 归因事件

每个对象都必须有：

- 唯一主键
- 来源系统
- 创建方式
- 核心状态字段
- 与其他对象的关联关系

### 6.2 统一归因口径

至少要统一这几个问题：

- 来源对象是谁
- 入口对象是谁
- 站点对象是谁
- 活动对象是谁
- 奖励对象是谁
- 订单对象是谁
- 一个用户最终归因给谁

### 6.3 统一用户身份口径

至少明确：

- fan
- user
- member
- identified_user
- oa_fan

这些标签的定义、来源、切换条件、页面展示口径必须统一。

### 6.4 站点福利结果页

必须补成真正的站点维度结果页，至少可回答：

- 该站点当前命中哪些活动
- 该站点当前可用哪些卡券
- 默认推荐哪一个
- 来源入口是什么
- 为什么命中 / 为什么未命中

### 6.5 生产级验收清单

每条主链路都要形成验收卡：

- 输入来源
- 关键写表
- 关键读表
- 用户端表现
- 管理端回查页
- 审计字段
- 异常兜底

## 7. 建议优先级

### 第一阶段：先做治理，不再盲目扩功能

优先级最高的 4 件事：

1. 输出全系统数据地图
2. 输出统一归因口径文档
3. 输出主链路生产验收清单
4. 把站点福利页补成正式结果页

### 第二阶段：补生产级对账与审计

建议补：

1. 活动参与对账
2. 发券对账
3. 积分发放与扣减对账
4. 商品兑换与履约对账
5. Agent 动作日志审计

### 第三阶段：补环境与部署标准

建议补：

1. 本地开发环境标准说明
2. 测试环境标准说明
3. 生产环境网络与依赖说明
4. 数据库与向量能力的环境依赖说明

## 8. 生产级达标标准建议

判断某个模块是否达到生产级，至少满足以下条件：

- 数据来源明确
- 写入链路明确
- 回查链路明确
- 异常路径明确
- 页面展示与数据库口径一致
- 可做最小审计
- 可做最小对账
- 环境依赖明确

如果只满足“页面能打开、接口能返回”，不应认定为生产级。

## 9. 当前建议

当前不建议继续无序扩页面。

更建议的推进顺序是：

1. 先完成《全系统数据地图》
2. 再完成《归因口径说明》
3. 再完成《主链路生产验收清单》
4. 最后继续扩管理端与用户端页面

## 10. 结语

当前系统最值得肯定的是：

- 福利中心主链路已经从“概念验证”进入“可生产化收口”的阶段

当前最需要警惕的是：

- 不要因为页面越来越像后台系统，就误判为“全系统已经生产级”

真正的生产级标准，核心不在页面多少，而在于：

- 数据是否统一
- 归因是否可信
- 审计是否可回查
- 主链路是否可对账
